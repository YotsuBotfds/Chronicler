# Viewer performance, October 2026

Branch `perf/viewer`, from `main` `2f654a8` (PR #49). Viewer only: no
Python, simulation, bundle format or transport change. At every sampled
turn and panel the two builds render the same DOM on two generated
bundles and two fixtures ([Equivalence](#equivalence)), and the as-of-turn
tests of PRs #45 and #49 pass unchanged.

An external review measured the entry chunk at about 777 KB minified
(230 KB gzip; 791 KB at `2f654a8`) and suggested lazy-loading the heavy
panels, decoding large bundles in a worker and reusing event and history
lookups while scrubbing. All three are done; the measurements below are
interleaved A/B runs of the `2f654a8` build and this branch's build.

turn barely moves: on this machine it is set by Chromium's layout, text
shaping and painting of the changed DOM, which is the same in both builds
([Scrubbing](#scrubbing)).

## Method

* **Script.** `viewer/scripts/perf-viewer.mjs` (committed) serves each
  production build (`npm run build`) from its own local static server and
  drives it in headless Chromium through Playwright. `sizes` reads the
  chunks; `run` takes, per sample and in a fresh browser context: first
  contentful paint and the shell's first frame; the bundle load from the
  file input's `change` event to the frame after the first overview render
  with the bundle's data and the systems panel (the same moment in both
  builds); the long tasks (over 50 ms) in that window, their total blocking
  time (each task's time over 50 ms, summed) and the longest; the JS heap
  after a forced garbage collection; and scrubbing. A scrub step is a click
  on the timeline track at the next turn, timed to React's commit (mutation
  records arrive after it: "script"), to a forced layout after it, and to
  the frame after it ("frame"). Patterns: 100 consecutive turns from 40% of
  the run and 50 seeded random jumps on the overview with the Event Log
  open; 50 and 50 on the Campaign surface (wars layer and tab); 30 and 30
  on the overview with an event pinned in the inspector.
* **Bundles** (kept out of git), written by the no-Rust venv
  (`uv sync --frozen`, Python 3.13.17, no `chronicler_agents`),
  `PYTHONHASHSEED=0`:
  * guard: `python -m chronicler.main --seed 1 --turns 500 --civs 5
    --regions 10 --agents off --simulate-only` (the size-guard world of
    `tests/test_bundle.py`): 6,893,109 bytes, version 6, 500 snapshots,
    6,029 events, 10 civilizations over the run. (`bundle-v6.md` recorded
    8.6 MB for this world at PR #34; later history changes shrank it.)
  * proc32: `--seed 42 --turns 300 --civs 10 --regions 32 --worldgen
    procedural --agents off --simulate-only`: 24,600,392 bytes, 300
    snapshots, 19,060 events, 3,212 named events, 25 civilizations.
* **Machine.** Linux, 4 cores shared with another agent's validation gates
  (load average 5 to 8 throughout), Node 22.22.0, Playwright 1.63,
  Chromium 153 headless, viewport 1920 x 1200, the script under `nice`.
  Wall times on this machine are noisy; every figure is the median of 5
  runs per build with the range (min-max) of the runs. Each round loads
  each bundle in each build, alternating the build order between rounds.
  For a scrub pattern a run's figure is its median (or 95th percentile)
  step; the table gives the median and range of those over the runs.
* **Builds.** `main`: `2f654a8`'s viewer, entry `index-BVdsInve.js`.
  Branch: entry `index-pfIHuVas.js` (`3957532`; later commits change tests,
  scripts and docs only).

## Load

On `main` one task reads, parses and expands the file (the longest task
above, 347 and 824 ms) and two or three render tasks follow. On the
branch the main thread only receives the decoded parts and renders; the
worker's own phases (its user-timing mark, 5 runs each):

| Bundle | Worker starts after `change` | Read | Parse and decode | Main-thread receive, total (parts, longest) |
| --- | ---: | ---: | ---: | ---: |
| guard | 22-79 | 11-57 | 163-221 | 86-163 (35 parts, 8-29) |
| proc32 | 18-56 | 33-96 | 564-624 | 234-372 (33 parts, 24-49) |

The time to the first overview stays about the same because two things
cancel: the history expansion is 2.3-2.4 times faster (change 3), but the
decoded bundle has to cross to the main thread (structured-clone
serialization in the worker, deserialization on the main thread) and the
worker has to start. No part takes 50 ms to receive, so the remaining
long tasks (the longest 69-331 ms over the runs) are the renders: the
first overview mounts every panel and builds the indexes. Two
earlier versions were measured and replaced: posting the bundle as one
message left a 302-336 ms receive task on proc32 (single runs), and the
worker path before the codec fast path took 1,555 ms (1,480-1,788)
against `main`'s 1,194 (1,095-1,353) on proc32 (3 interleaved runs).

The heap after the load is 2.1 and 5.1 MiB smaller on the branch; the
cause was not investigated (the bundle's values are the same, and the
parts lose sharing only between consecutive history slices).

Files under 1 MiB still decode on the main thread: there a worker's start
and the copy back would cost about as much as the decode (on `main` the
6.9 MB file took one 347 ms task, about 50 ms per MB).

Script per step falls 22-69%. The rest of the frame does not: a trace of
`main` on the guard bundle (20 consecutive steps) spends about 210 ms of
main-thread task time per step, of which 37-47 ms is script (Chrome's
`ScriptDuration`; 18 ms on the branch in a paired run); the style and
layout pass takes 40-64 ms, nearly all of it text shaping
(`InlineNode::ShapeTextIncludingFirstLine`, 54 ms of a 59 ms layout) for
the roughly 2,700 characters of new event, systems, inspector and
language text each step brings; pre-paint takes 18-94 ms and paint 5-30
ms. Those follow from the DOM changes, which are what the viewer shows
and are identical in both builds. This is headless Chromium with
software rasterization and without the shell's named fonts; on a desktop
browser the frame is likely shorter and the script share larger, which
was not measured. Random jumps keep more script time than consecutive
steps because a jump replaces most of the lists' rows.

The forced layout after the commit measures longer on the branch (for
example 8.2 -> 10.5 ms on guard consecutive, 11.4 -> 17.4 ms on proc32)
for the same DOM mutations, so script plus layout changes by -30% to
+11% on guard (four of six patterns within 5%) and falls 7-24% on
proc32. The cause was not found. The frame, which contains both, is
6-19% shorter on proc32 and -12% to +3% on guard, within the run-to-run
ranges there.

## Changes

1. **Lazy panels** (`components/phase75/lazyPanels.ts`, `lib/preloadable.ts`).
   The systems tabs (all fourteen panels and Recharts), the languages
   inspector, the region history inspector, the Batch Lab panel, the batch
   comparison overlay and the intervention panel are dynamic imports. None
   is on the first screen (setup, before a bundle). `preloadable` wraps
   `React.lazy`: a panel whose chunk has arrived renders at once, with no
   Suspense fallback even for a frame, and a mounted instance keeps the path
   it started with, so the chunk's arrival never remounts it or loses its
   state. The shell fetches the chunks when the browser is idle after the
   first paint and again when a bundle starts loading, so they are
   normally there before they are needed. Until then a panel shows
   `PanelLoading`: a polite, `aria-busy` status line in the panel's frame.
   A chunk that fails to load shows "Could not load the ... Reload the
   viewer to try again." in place, not the error boundary.
   The lazy panels' stylesheets stay in the entry stylesheet, imported in
   their old order: loaded with their chunks, they came after the shell's
   and won the cascade where selectors tie, which moved the systems panel
   (the equivalence check caught it, 52 differing captures on the guard
   bundle, before the fix). The entry stylesheet is `main`'s plus the
   placeholder's rules (51,113 -> 51,290 bytes).
2. **Worker decode** (`lib/bundleDecode.ts`, `lib/bundleDecode.worker.ts`,
   `lib/bundleFile.ts`, `hooks/useBundle.ts`). A file of 1 MiB or more goes
   to a dedicated worker as the `File` itself (no copy on the main thread).
   The worker reads it, decodes the text (byte order marks as before),
   parses, runs the loader's checks and the version-6 expansion
   (`bundleCodec`, the same code as the main thread) and hashes the
   original bytes (alongside the parse). It posts the bundle back in parts:
   each top-level field in key order, the history in slices of 25
   snapshots and the timeline in slices of 2,000 events, so the main thread
   receives (structured-clone deserializes) it in many short tasks instead
   of one; the world state's `events_timeline` and `named_events` are
   pointed back at the top-level lists, as the decoder makes them. Nothing
   renders until the last part is in. One worker per load, terminated when
   it answers, when a newer upload supersedes it, or on unmount. Without a
   worker (jsdom; a worker that fails to start, crashes or sends a reply
   that cannot be received) the file is decoded on the main thread as
   before. Malformed files give the same messages either way: the loader's
   `INVALID_HISTORY_DELTA` ("Invalid bundle history: history_delta[3]:
   ...") for a `BundleDecodeError`, "Failed to read file", "Could not read
   bundle: ...". The loading state ends whatever fails.
3. **Codec fast path** (`lib/bundleCodec.ts`). The common object patch
   (no reserved key, no `__proto__` key on either side) is applied to a
   shallow copy of the previous object, which keeps its key order; changed
   keys are replaced in place and new ones follow in the patch's order,
   which is the order the reference builds. Every other patch, and every
   malformed one (any `BundleDecodeError` below it), goes through the
   unchanged reference implementation, so values, key order and error
   messages (the first error in the reference's order) are the same.
   History decoding takes 2.3 to 2.4 times less time (Node, same process,
   4 repetitions: guard 145-265 -> 62-77 ms, proc32 493-544 -> 213-252 ms),
   on both the worker and the main-thread path.
4. **Scrub indexes** (`lib/bundleIndex.ts`). The Event Log (the 24 latest
   events up to the turn, a focused civilization's first), every systems
   tab's event list (`eventsOfTypes`), the pinned event (`eventByKey`), its
   causes and consequences, a region's terrain transitions, the wars
   layer's raids, mass migrations and the techniques practised by the turn
   filtered and sorted the whole timeline or history on every render. Each
   is now a lookup into an index built once per array: the timeline in
   latest-first order (ties in timeline order) with binary search by turn,
   per actor, per type list, per type, by key, by id and by citation; the
   first turn of each technique. Indexes are keyed by the identity of the
   `history` or `events_timeline` array (a WeakMap, as `civRows` already
   did): a new upload, a Batch Lab bundle and every live `turn` message
   bring new arrays (`useLiveConnection` replaces them, never mutates them),
   so they get new indexes and the old ones are collected with their arrays;
   an array whose length changed in place is indexed again. Every lookup
   returns the same events in the same order as the filter it replaced.
5. **Turn-independent parts not re-rendered.** The timeline rail's era
   bands, narrated spans (one per chronicle entry: 500 on the guard bundle)
   and named-event markers, and the systems strips' segments, are memoized
   components; the era bands, narrated spans, markers, atlas frame and the
   strips' accessible labels are computed once per bundle. The DOM is
   unchanged.

## Equivalence

* **Rendered DOM, before and after** (`viewer/scripts/viewer-equivalence.mjs`,
  committed). Both production builds are driven through the same sequence:
  upload, then the whole shell's DOM captured once stable over two frames
  (Recharts and React generated ids normalised; no loading placeholder
  left) on the overview at 12 turns (1, 2, 3, the quarters, the last two,
  4 seeded random turns), and at the first, middle and last turn for each
  systems tab, each map layer, the Event Log, two selected regions, the
  Character, Trade and Campaign surfaces and the region history inspector,
  plus a pinned event before, at and after its turn. Result: guard 95
  captures in 28 states (12.6 MB of DOM per build), proc32 95 captures in
  28 states (13.9 MB), the systems fixture 92 in 27 and the version-6
  transport fixture 94 in 29 (both under 1 MiB: the main-thread path):
  **0 differences**, no console error or warning in either build. The
  branch decoded both generated bundles in the worker (its user-timing
  mark), `main` on the main thread.
* **Index lookups, turn by turn** (`lib/__tests__/bundleIndex.test.ts`).
  Each lookup against the filter it replaced (copied from `2f654a8`) at
  every turn: five synthetic timelines (ties, out-of-order turns, repeated
  ids and actors, cyclic causes, region names that prefix each other), six
  fixtures, and with `VIEWER_EQUIVALENCE_BUNDLES` the two generated
  bundles (every 7th turn); live appends (a new array per turn), an
  in-place append and growing histories. Reversing the tie order fails 13
  of its 14 cases.
* **Live streaming** (`components/phase75/__tests__/AppShell.live.test.tsx`).
  The systems fixture streamed turn by turn as `useLiveConnection` does:
  at each streamed turn, and scrubbed back, the mounted shell's DOM equals
  a fresh shell's on a copy of the same bundle; an intervention's replaced
  last snapshot too. Keying the timeline index by something that survives
  an appended turn fails both cases.
* **Codec fast path** (`lib/__tests__/bundleCodecFast.test.ts`). 600
  random histories, every prefix decoded both ways: 2,022 valid prefixes
  identical (values and key order) and 533 malformed ones with identical
  messages; the fixtures and (with the variable) both generated bundles
  identical. Dropping the `__proto__` guard or letting a key order through
  the fast path fails it.
* **Worker** (`hooks/__tests__/useBundleWorker.test.ts`). The worker's
  handler gives the main thread's bundle, identity and error messages; the
  parts reassemble to the same bundle and key order; `useBundle` with a
  stand-in worker loads through it, falls back when it crashes, stops a
  superseded one and one left at unmount. The browser path is the
  Playwright runs above.
* **As of the turn.** The tests added by PRs #45 and #49
  (`AppShell.scrubbed`, `AppShell.founding`, `AppShell.pruned`,
  `useBundleMalformed`, `bundleCodecMalformed`,
  `useLiveConnection.parity`) pass with their assertions unchanged; the
  AppShell test files only preload the lazy chunks first.

## Not done

* The live paths still parse on the main thread: a Batch Lab
  `bundle_loaded` message and a reconnect `init` arrive as one WebSocket
  text message holding the decoded bundle, which `JSON.parse` reads before
  the type is known. Moving them to the worker needs a transport change
  (for example the version-6 encoding over the socket) and was left alone.
  Live `turn` messages are small.
* Scrub frames remain rendering-bound here (above). Reducing them would
  mean changing what is drawn (fewer rows replaced per step, lighter
  panel effects) or re-rendering the Recharts charts without their
  per-turn reference line; each is a visible or structural change, not
  done in a no-behaviour-change branch. The charts still re-render every
  turn.
* The upload is about as fast as before on the guard world and 12%
  slower on proc32 (the price of the worker's copy back); the page stays
  responsive meanwhile. A pre-started worker (about 20-80 ms) and sending
  the non-history fields while the history decodes were not tried.
* The longer forced layout on the branch and the smaller heap after the
  load are measured, not explained.
* Browsers: headless Chromium only. Module workers (`type: "module"`;
  the worker chunk is a classic-compatible IIFE) and the fallback were not
  tried in Firefox or Safari; no device QA.
* No native or hybrid bundle (the venv has no extension); no simulation,
  gate or full Python suite run (no Python change).
